# 草原二十事件追踪接入说明

> 此文为10月18日框架阶段的历史说明；当前数值、正式执行器和地编地图已经接入，以《二十事件整合与验收说明_2026-10-19.md》及运行配置为准。

本轮实现二十个事件的状态追踪、条件检测、持久化请求与触发调度。地图点位和关联由地编填写；剧情播放器、正式资源服务和战斗服务通过下述接口接入。开场的独立2.5D演出不在本轮生成。未确定的奖励、阵容、属性口径和支付规则保持待配置，对应操作会返回具体缺项原因。

内容依据 GitHub 提交 [816606c 的事件目录](https://github.com/Carloramia/SupremePoorGuy/tree/816606c8ef033cc69e30998e5c4b48f9a15dbbc2/UI%E8%B7%B3%E8%BD%AC%E5%8E%9F%E5%9E%8B/%E4%BA%8B%E4%BB%B6)，沿用原有稳定事件ID。来源快照位于 `Content/Events/Source/GrasslandEvents.source.json`，原稿含20个事件及3个辅助入口；运行配置只登记20个事件。城市和罗瓦常驻入口由表现层根据事件状态路由。对白没有改写为可执行节点。

## 二十个事件的追踪规则

入口键是事件内的逻辑标识，不是已经放置的地图对象ID。`available` 为初始阶段，`complete` 为持久终局；其他阶段及待处理请求恢复后继续使用原请求。

| --- | --- | --- |
| 01 火速任命 | `opening` | 外部开场播放器接入；交接对白结束后提交特令事务，成功才完成，不自动在地图播放 |
| 02 小树守卫 | `tree` | 已成功召唤且该批安置完毕，当前有出战怪物，再返回安全地图时排队；明确开始演出后移除队列，匹配的真实胜利才进入后续结算 |
| 03 图书馆开门日 | `library` | 对话结束后提交奖励事务；基础符文配置为 armor、health、attack，私房钱仍待填，缺项时不假定为0 |
| 04 防卫预算 | `center`、`defense_target` | 城主接取后追踪指定战斗请求；其胜利保存后允许回城提交，普通战斗胜利无效；重访不重置目标 |

## 地编接入

GameRoot 的 `story_event_bindings` 是可选字典，保持默认空值，没有修改当前地图文件、点位、入口位置或敌军。绑定格式为：

```gdscript
{
    "真实map_id:真实location_id": {
        "event_id": "QST_GRASS_007",
        "entrance": "donkey"
    }
}
```

从实际地图读取ID，不使用上述示意键直接发布。绑定入口会在原生地图确认抵达且可交互后调用 `route_story_arrival()`；仅选中标记或开始寻路不会登记已见。旧地图也从其正式 `location_interaction_started` 回调转发。此接口采用显式字典，不把现有地图中的任意 `event_id` 字段自动解释为本事件系统绑定。

已绑定的到达同时计入新手教程的“探索边境”。事件完成只停止该事件入口回调；共享城市对象的保留与隐藏交由地编和表现层依据状态处理，不删除整座城市。同一城市的多个事件选项应由城市面板分别调用对应逻辑入口。

## 剧情和触发调度接入

1. 监听 GameRoot 的 `story_event_entry_ready(event_id, entrance)`，准备对应剧情入口。此时仅表示抵达已确认，尚未开始播放或完成对白。
2. 监听 `story_event_due(event_ids)` 接收02号和15号自动触发提示。队列有序、持久保存；未接监听器时不会悄悄消费。
3. 准备实际播放时调用 `GameRoot.open_story_event(event_id, entrance)`，读取返回的 `event.conversation`。成功后才视为演出已触发并移除自动队列。
4. 只在相应对白结束或玩家明确确认后调用 `GameSession.story_event_action(event_id, branch, conversation, payload)`。会话ID必须是本次打开返回值；旧窗口回调会被拒绝。
5. 普通关闭提交 `leave`，09号也支持 `close`；它们不发奖、不完成、不抹除已接取阶段。已有外部请求时，关窗不能撤销请求，应由表现层关窗后保留原请求。

安全演出要求：处于大地图、没有其他纸面窗口或控制台、没有召唤结果待安置、没有部署/战斗/结算请求，也没有正在返回主菜单。队列通知不会自动启动战斗或代替剧情播放器。01号继续由独立开场场景明确接入。

玩家展示读取 `story_event_view()`：只给当前阶段的分支和待处理请求ID，不暴露未来献祭条件。`pending_story_request()` 返回宿主执行所需完整计划，只供正式服务和调试使用，不直接发送给玩家UI。事件任务与原有四条新手任务使用不同进度字段，没有把二十条事件塞入新手任务清单。

## 资源和战斗回执

`story_event_action()` 只保存意图，返回稳定的 `request`。重开面板、连点和读档都复用原请求；计划中的阵容、奖励及下注轮次随请求冻结，重试不得重新抽取。先执行正式服务，再向 `commit_story_receipt(receipt, apply_business)` 提交：

```gdscript
var receipt = {
    "request_id": request.request_id,
    "event_id": request.event_id,
    "stage": request.stage,
    "branch": request.branch,
    "kind": request.kind,
    "outcome": "success",
    "committed": true
}
# apply_business(save_dictionary, request) -> String
# 只修改传入的正式存档字典；成功返回空串，失败返回原因。
var ok = session.commit_story_receipt(receipt, apply_business)
```

资源适配器必须负责真实的余额、库存、扩圈布局、实例回收、容量和安置规则；框架没有生成假的奖励或替代战斗。它只允许宿主提交回执，玩家UI不能直接构造成功回执。事务回调内禁止嵌套保存，也不能在回调外先做不可回滚的资源写入；正式资源修改、事件状态及去重记录使用同一份存档提交。保存失败会一起回滚，适配器失败也不推进。

战斗回执附带相同 `battle_id`，`outcome` 使用真实的 victory、defeat、retreat、interrupted、load_failed 或 draw。观战还必须提供 `winner: one/two`，不能读取普通玩家战斗的胜负标记替代获胜方。战斗胜利通常会生成 `_settle` 奖励请求，收到该请求的资源提交成功才完成事件；04号先登记清剿目标，06号保留独立拾取记录。

18号可选择一次原子事务完成消费与奖励；若正式服务需要分两次保存，先提交 `kind: sacrifice, outcome: consumed, committed: true` 并在资源回调扣除实例。框架保存消费回执后创建 `_reward` 请求，保留 `consumed_ids`，原阶段不推进。重载后只执行该奖励请求；成功后才显示下一要求。`reward_retry` 返回同一待处理请求，不再次消费。献祭payload必须包含 `monster_ids` 及 `confirmed: true`；提交前重读正式库存，检查数量、特征、不可回收、锁定、战斗占用与至少保留1只。

20号依次生成下注资源请求、`_watch` 真实观战请求和 `_settle` 账务请求，最后一步成功后次数才加1。赢家返还2B，败方返还0的测试配置只有在规则明确填入后才可用。正式配置中的失败支付、平局与中止规则仍为 null；不会实际开放下注。当前框架只支持将平局和中止保留原请求待处理，不擅自退款、扣第二次本金或消耗轮次。

## 时间服务接入

正式时间服务每次推进、跨日跳过或恢复权威时间后调用 `set_story_game_day(game_day)`，使用游戏内累计天数，可包含小数。禁止传入电脑日期、Unix时间或帧数；框架不自行推动 `data.day`。游戏时间不允许倒退。成功购买时从此时间取值，保存 `purchased_day` 和 `due_day = purchased_day + 4`，到期判定使用 `>=`。

到期队列随存档恢复，即便此时战斗、结算或其他对话未结束，也不会丢失或重计时。实际打开鬼魂剧情才标记已触发；未完成的对白和发奖请求仍可以继续。

## 待配置项与检测口径

在 `GrasslandEvents.json` 的 `bindings` 中补齐以下项。null 是明确缺项，只有策划明确“不发奖励”时才可填 `{ "magic":0, "runes":[], "relics":[] }`。

- `rewards`：魔力、现有符文/奇物解锁；可选 `items`、`monsters` 为 `{id,count}` 数组，由正式资源服务验证ID和处理安置。不替尚未定义的物品或怪物预设造默认内容。
- `battles`：实际 `battle_map_id`、`enemy_config_id`。观战还需 `other_side` 的场景与预设；助战计划明确 `include_helped_ally: false`，观战计划明确不部署玩家怪物。
- `monster_fields`：正式字段名称。攻击力、大型、皮毛、飞行、蛇类、手数、足数都不从显示名称、体型图片或中文词条猜测；攻击阈值另填 `attack_threshold`。
- `engine_max_stage`：召唤阵正式扩圈上限。资源服务仍需真实校验扩圈布局与余额。
- `bet_rounds`：四轮的两方手填阵容；本金固定10、20、50、100。失败策略、平局策略、中止策略均需明确，当前未开放。
- 血雨的作用、范围、时长和覆盖规则保留未定，本轮没有调用默认天气效果。

03号原型的符文仍默认全部开放。正式奖励适配器应将解锁集合去重，已拥有不重复添加、不自行折算魔力。旧存档仅自动保留现有可靠的召唤与队伍事实供02号检测，不能从“去过地图”推断其余事件已完成或已领奖。

## 验证

使用 Godot 4.7.2，隔离测试存档运行：

```powershell
godot --headless --path <it-is-time目录> --script res://Tests/Integration/ValidateStoryEvents.gd
godot --headless --path <it-is-time目录> --script res://Tests/Integration/ValidateStoryEventHost.gd
```

状态机验证覆盖二十条事件、会话与战斗关联、奖励缺项、互斥路线、双节点发现顺序、库存实时判定、逐次献祭与消费恢复、时间跳过和读档、赌局四轮与重复回执，以及正式存档失败回滚。宿主验证覆盖返回地图后自动检测、弹窗安全门、真实抵达回调、新手探索兼容及通知不逐帧重发。既有新手任务、GameRoot和原生大地图的集成测试同时回归。

上述验证证明框架与既有接入点工作。地图绑定、剧情播放器、真实观战、资源/天气适配和未定玩法参数补齐后，仍需按源目录的程序监听清单完成内容联调；本轮不将这二十条草稿标为游戏内全部可玩。

## 系统隔离口径

召唤和仓库是两个独立的业务职责，不把仓库放进召唤系统的内部文档，也不要求进入召唤页才能管理怪物。各自导引单独保存，不复制对方的完整规则。

**现状：页面和纯召唤规则已分离，流程与存档尚未完全解耦。** 0.5使用共用纸雕主题、独立分件和画板动画，未拆分共享业务控制器，不声称已经形成两个可脱离宿主独立运行的插件。

| 归属 | 可优先修改的范围 | 不应自行修改 |
|---|---|---|
| 召唤负责人 | `Scripts/Ritual/`，`RitualPanel.tscn`，符文／奇物组件，书本入口；具体列表见自身导引 | 仓库筛选、改名、队列规则；公共存档格式与主题 |
| 仓库负责人 | `WarehousePanel.tscn`、`MonsterDetail.tscn`、`PartySidebar.tscn`；具体列表见自身导引 | 法阵识别、符文占格、召唤扣费与生成；公共存档格式与主题 |
| 共同协商 | `MonsterCard.tscn`、`MonsterResultCard.tscn`、`MonsterPortrait.tscn`、`ResultsPanel.tscn`；召唤结果与安置交界 | 两边各复制一套怪物数据、各自重复生成同一批怪物 |
| 公共集成层 | `GameDemo.gd`、`PrototypeState.gd`、`WorldView.gd`、`ModalHost.tscn`、`AppShell.tscn`、共享Theme | 两位接管成员各自无协调重写同一公共文件 |

现有 `GameDemo.gd` 同时编排两套页面，`PrototypeState.gd` 同时保存产出与怪物位置。这两个文件的改动需要集成人员协调。各系统导引已按方法列出归属与交界，不能仅凭文件夹位置推断独立性。

## 两系统交界：生成与安置

1. 召唤负责校验法阵、扣费、生成并持久化怪物实例；随后显示喷涌。
2. 怪物使用唯一 `id`，不能在仓库打开或演出结束时重新随机生成。
3. 结果安置负责将同一实例从 `pending` 转到 `warehouse` 或 `team`；关闭结果时剩余入库。
4. 仓库负责人维护位置转移、队列上限和改名；召唤负责人不复制这些规则。
5. 目前由公共 `PrototypeState` 保证失败回退和一次性保存；未来拆服务时保留这一事务边界，不另建两个互相覆盖的存档。

未来若完成控制器／服务物理拆分，必须先更新两份导引、这份索引与测试，再迁移调用。规划中的接口名称不等于现在已经存在的API。
